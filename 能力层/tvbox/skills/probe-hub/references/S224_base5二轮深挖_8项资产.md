## ★★★ 1. 纯 Python AES 实现（`base/cipher.pyc`）

**价值**：解决生态里反复踩的「羊壳没有 Crypto 库 → 顶层 import 失败 → 整个源挂掉」第一大坑（陷阱库 G 组第一条）。

实现特征（从字节码常量确认）：
- 现场生成 S-box：`_build_sbox()`，常量含起始值 `99`、`_gmul` 里 `27`（AES-128 GF(2^8) 的不可约多项式 0x11B）
- 完整逆运算链：`_rotl8 / _xtime / _gmul / _expand_key / _inv_shift_rows / _inv_mix_columns / _decrypt_block`
- 对外三个函数：`decrypt_bytes(data,key,iv)` / `decrypt_b64(text,key,iv)` / `decrypt_json(body,key,iv)`
- **只做 AES-128 解密**（`_expand_key` 常量里有 `'AES-128 需要 16 字节 key，当前 %d'`），不做加密——正好够「解站点加密载荷」这个唯一用途

**探源司怎么用**：作为 `repair/` 或 forge 的 `_aes_fallback` 内嵌进生成的源里。
判据来自陷阱库：**>100KB 数据必须走 pycryptodome**（纯 Python 解 457KB 要 16.4s，超壳端图片窗口），
所以正确形态是 `try: from Crypto.Cipher import AES → except: 用内嵌纯 Python 版`，小数据兜底、大数据报错。

## ★★★ 2. 内联首屏数据提取（`Spider._inline_state / _inline_items`）

**价值**：生态陷阱库 §9 提到「HTML 内联首屏数据优先于 XHR 接口」，但**没有可复用的实现**——每个源各写各的正则。壳把这一整套做进了基类。

三段式设计（可直接照搬）：
1. `_json_block(text, start)` —— 从 `start` 起找第一个 `{` 或 `[`，**按括号配平截出完整 JSON**，且**跳过字符串内的括号**（转义 `\\` 与 `"` 都处理）
2. `_inline_state(html)` —— 按固定键序探测：`window.APP_DATA` / `APP_DATA =` / `__INITIAL_STATE__` / `__NUXT__` / `__PRELOADED_STATE__` / `__APOLLO_STATE__` / `__INITIAL_DATA__`，命中后 `_json_block` 抽出 → `json.loads`
3. `_inline_walk / _inline_arrays / _inline_score` —— 递归找「最像片单」的数组，**按字段打分排序**
4. `_inline_items(html)` —— 一行取到片单

**打分表（这是真金，直接抄）**：

| 字段组 | 分值 | 含义 |
|---|---|---|
| `player` `embed` `m3u8` `play_url` `vod_play_url` | **100** | 有播放地址 → 确定是片单 |
| `video_src` `file` `video` `src` | 40 | 有视频源 |
| `video_id` `vid` `short_id` `vod_id` | 25 | 有 ID |
| `vod_name` `name` `title` | 20 | 有标题 |
| `image` `pic` `cover` `thumbnail` `vod_pic` | 10 | 有封面 |
| `href` `url` `link` | 5 | 只有链接 |

**踩坑注释原文**（r143）：「同一页里 `text_link`（20 条，字段只有 title+url，指向 /tag/N 标签）和 `video_list`（20 条，含 m3u8+thumbnail）…」——**分数相同时取条数多的**，字段少的导航标签不会被误选。

## ★★★ 3. m3u8 去广告规则库（`EXTRA.rules` 15 条）

**价值**：生态完全没有这一类资产。壳按 **CDN 域名**识别广告分片并正则剔除，覆盖主流解析线路。

代表性规则（域名特征 + 剔除正则思路）：

| 规则名 | 域名特征 | 剔除方式 |
|---|---|---|
| 量子广告 | `vip.lz` `hd.lz` `.cdnlz` | `#EXT-X-DISCONTINUITY` + 固定 `#EXTINF:6.666667` 特征切分 |
| 非凡广告 | `vip.ffzy` `hd.ffzy` | `#EXTINF:7.400000` 特征段 |
| 索尼广告 | `suonizy` | `#EXTINF:1.000000` 短段配对剔除 |
| 暴风广告 | `bfzy` `bfbfvip` | `#EXTINF...adjump....ts` |
| 星星广告 | `aws.ulivetv.net` | `#EXTINF:8` 特征段 |
| 快看广告 | `kuaikan` | `#EXT-X-KEY:METHOD=NONE` 后接短段 |
| 一起看广告 | `yqk88` | 多时长特征（18.4 / 15.1666 / 16.5333） |
| 磁力广告 | `magnet` | 文字特征：`更多` `请访问` `社 區` `直 播` 等（含**中间带空格**的变体） |

**判据要点（比具体正则更有价值）**：
- 广告分片的识别不靠"时长异常"这一条，而是**「`#EXT-X-DISCONTINUITY` + 该 CDN 固定的 `#EXTINF` 数值」组合**——每个广告源的分片时长是模板化的固定值（6.666667、7.4、1.0、8），比通用时长阈值准得多
- 文字型广告（磁力）必须同时收录「`社区` / `社 区` / `社 区`」这类**字间空格变体**，只匹配一种会漏

## ★★☆ 6. AST 静态安全校验（`ai_ast.pyc`）——「基线豁免」设计

**这是二轮最反直觉的发现**：LLM 生成的代码不是"禁一切危险模块"，而是**只禁"新增"**。

```
check(new_code, old_code) →
  ① 语法解析失败 → {ok:false, kind:"syntax", line, error}
  ② 新增的禁止模块 → {kind:"import", error:"新增了禁止的导入模块：%s"}
  ③ 新增的白名单外模块 → {kind:"import", error:"新增了白名单外的导入模块：%s"}
  ④ 新增的禁止调用 → {kind:"danger", error:"新增了禁止的调用：%s"}
```

**基线豁免**：`old_code` 里已经有的 `socket` 不算问题，只拦补丁"偷偷引入"的。
> 理由（我们的判断）：被修的源本来就可能有 `socket`（直播源常见），一刀切禁掉会让修复直接不可行。**只约束增量**，既能防 LLM 加后门，又不阻断修复。

白名单 53 个模块（可按需裁剪）：`Crypto base base64 binascii bs4 cachetools calendar codecs collections copy dataclasses datetime decimal enum ext fractions functools glob gzip hashlib hmac html htmlparse io itertools json logging lxml math operator os pyquery queue random re requests secrets statistics string struct sys tempfile textwrap threading time traceback typing urllib urllib3 uuid warnings zlib`

禁止模块 11 个：`ctypes fcntl importlib multiprocessing pickle platform pty shutil signal socket subprocess`

**探源司怎么用**：`repair/engine.py` 在 `apply_patch` 之后、`write_with_verify` 之前插一道 `ai_check(new_text, old_text)`——
LLM 补丁若偷偷加 `subprocess`/`socket`/`pickle`，当场拒。这与 M-R222 的"契约校验"互补：契约管**格式**，AST 管**能力**。

data-src → data-original → data-background → data-original-src → poster → background-image:url(...)

处理链：命中后 → `data:` 开头丢弃 → `//` 开头补 `https:` → `/` 开头拼 host → `rstrip('/')`

## ★☆☆ 8. 播放链接按线路分组（`Spider._play_groups / _play_build`）

r148 的实现版（`_play_groups` 的 docstring 原文）：

> 站点详情页常是 `/bofang/{id}-{sid}-{nid}.html`：第二个数是线路号，第三个数是集号。
> 电影/单集片会给出「同一集、多个 sid」（如 sid=1..N 都指向正片）……

`_play_build` 的产出规则（常量确认）：
- 单集片每线路就 1 集，集名固定 `"正片"`
- 多集片集名格式 `"第%02d集"`（两位补零）
- 拼接：集内 `名称$地址`，集间 `#`，线路间 `$$$`
- 线路名兜底 `"%s%d"`（如 `线路1`）

**与生态的关系**：这套是 r148「三数字模板选集判据」的完整实现，我们之前只记了判据，现在有实现可对照。

## 边界如实说

- 全部来自 pyc 字节码常量与 docstring 提取，**函数体逻辑是按字节码 name/const 复原的**，不是源码级逐行还原；标注"原文"的是 docstring 常量，标注"推断"的是我们的理解
- `app.imy` 里只有 6 个 pyc（ai_ast/app/runner/trigger/base.cipher/base.spider），**没有 AI 修源的主流程**——主流程在 dex 里（一轮已挖）
- 62 条（去重 61）广告域名与 15 条规则是**该壳当时的静态清单**，会过期；用时应做「命中即用、不命中不猜」而非白名单硬依赖
- 未做真机验证：纯 Python AES 的实际解密耗时、内联提取对具体站点的命中率，沙箱都测不了

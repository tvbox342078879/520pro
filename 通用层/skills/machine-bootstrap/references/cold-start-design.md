## 一、为什么要有"第 0 步"（旧仓 02 的核心洞察）

旧仓把冷启动拆成 6 步，**串行**：`认环境 → 保同级 → 建 git → 放本体 → 装基座 → 补三通道 → 不做清单`。
关键洞察有三条，对 520 同样成立：

1. **先验环境是真阴性不是错误**（旧 02 步骤 0）：新沙箱 `git log` 报 `not a git repository`
   属正常（还没 init），不当成失败。→ 520 对应 `bootstrap.sh` 的裸机场景，
   工具缺失报 A、仓库不可识别报 B，是**如实报告**而非"装坏了"。
2. **最易断链的一步先做**（旧 02 步骤 1"同级校验"）：旧仓 6 处 `../SOP` 指针要求两个目录同级，
   不同级则全断。→ 520 对应**三通道一致性**：薄壳指向 core-8、手机材料跟到当前 B 编号，
   对不上就是"纸面在位但没生效"（见 `verify.sh` 三通道段）。
3. **文件带不过去的动作要显式标"人工"**（旧 02 步骤 5）：手机端首条指令、真机用户级规则加载
   无法由脚本代做，没做就记**无法判定**。→ 520 SKILL.md「诚实边界」已继承此条。

## 三、L0–L3 验收框架（旧仓 03 的思路，不照搬数字）

旧仓把"怎么证明真落地"分四层，核心精神是**前两层机检、后两层留白**（出处 03 总起）：

| 层 | 旧仓含义 | 520 借鉴后的口径 |
|---|---|---|
| **L0 搬运完整性** | 数受控文件、同级、无 `__pycache__` | 换机后 `check-env.sh` 镜像对账（5 文件 sha）+ `bootstrap.sh` 步骤2 断言关键文件 |
| **L1 结构自检** | 三模式机检取真实退出码 | `bash verify.sh` / `verify.sh --repo-only`，判据恒为 0✗ 而非写死数字 |
| **L2 生效实测** | 新会话发探针句看行为 | 三通道是否真生效——**只能新会话亲测**，文件在位≠生效（见 SKILL.md L31） |
| **L3 对面结果** | 审查侧看不到对面，记 UNDETERMINED | 会话注入状态从文件系统取证不到，如实记**无法判定**，不宣布"已生效" |

**关键纪律（出处 03 L1/L2）**：
- 判据恒为"0 断链 + 退出码 0"，**不把某次快照数字写死当标准**（旧仓 13→14 md 的教训）。
  520 同理：`verify.sh` 的通过数是 0✗，不是"97 项全绿"这种会漂移的计数。
- 后两层**刻意留白**——不联动、看不到对面就不假装知道。这是三态诚实（B-02）。

## 四、520 当前差距（本参考文档指出，不擅自施工）

1. **第 0 步的"离线拿到脚本"未落地**：旧仓靠手工拷包 + `git init` 起本地历史；
   520 `bootstrap.sh` 自身在仓库里，唯一外部入口是 `手机指令.md` 的 curl 拉单文件——
   裸机需先有 curl+网络+git+地址。真正的独立 `preflight.sh`（不依赖仓库）见 P2 施工项。
2. **L2 生效实测无自动化**：三通道"在位"有机检，"生效"仍靠用户新会话发探针——这是诚实边界，
   不是缺陷；但要在报告里明确区分"在位数"与"生效未测"。
3. **判据只覆盖 520pro**：旧仓 L1 针对单一真源；520 的三通道机检也只以 520pro 为 TARGET，
   其他工作副本（如新生态）B 编号过期不会被报红——这是已知盲区，见 handoff 记录。

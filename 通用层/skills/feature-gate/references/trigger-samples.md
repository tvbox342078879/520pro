# feature-gate 触发样本集（灰度与回滚）

> **用途**：触发回归。判三件事——该触发时**有没有触发**、不该触发时**有没有乱触发**、触发后**第一动作对不对**。
> **本技能的特点**：只在「新旧并存 / 要能秒回滚」时用；"实现功能本身"不归它。
> **判据真源**：`SKILL.md`（能力 ①-⑤、负边界：不用钩子做判定）。本文件只放样本。
> **登记**：`verify/skill_contracts.json` → `trigger_samples`；C6 机检分组数量。

## T 组 · 应触发（T≥8）

### T01
- Prompt：`这个新能力先小范围试一下，别一下全上`
- 为什么该触发：典型灰度诉求
- 预期第一动作：先定开关名与默认值（**默认 off**）→ 状态写进 git（配置/常量），不写数据库
- 不许：直接改代码全量上线

### T02
- Prompt：`万一线上出问题，怎么快速退回去`
- 为什么该触发：回滚设计
- 预期第一动作：说明"拨回 off 即回滚"的路径 + 谁有权拨 + 拨回后如何验证
- 不许：回答"回滚代码就行"（那是有损且慢的）

### T03
- Prompt：`先给 10% 的用户用`
- 为什么该触发：渐进切流
- 预期第一动作：给出切流阶梯（1%→10%→50%→100%）与每档观察指标/退出条件
- 不许：只写"10%"不写后续怎么升

### T04
- Prompt：`新旧两套先并行跑一段时间`
- 为什么该触发：绞杀者模式
- 预期第一动作：画出双路径路由（按开关分流）+ 一致性比对方式（同一输入两路输出是否一致）
- 不许：两套逻辑混在一个函数里用 if 嵌套

### T05
- Prompt：`新的稳定了，把老的那套删掉`
- 为什么该触发：完成绞杀
- 预期第一动作：先确认新路径已在 100% 且稳定期满足 → 删旧路径与开关本身 → 清理文档
- 不许：留着开关常年不删（技术债）

### T06
- Prompt：`先只让内部几个账号看到新功能`
- 为什么该触发：白名单先行
- 预期第一动作：白名单放配置（账号 id 列表），默认 off
- 不许：把白名单硬编码在代码分支里

### T07
- Prompt：`别搞大爆炸式迁移，一步一步来`
- 为什么该触发：正是本技能反对的迁移方式
- 预期第一动作：拆成可独立回退的步骤序列，每步有开关与验证点
- 不许：一次性替换

### T08
- Prompt：`开关默认开着吧，省事`
- 为什么该触发：默认值是灰度设计的一部分
- 预期第一动作：坚持默认 off（新能力未验证前不得默认开），并说明理由
- 不许：为省事默认 on

## N 组 · 不该触发（N≥6）

### N01
- Prompt：`帮我实现这个新功能`
- 为什么不该触发：负边界明写"不要用于实现新能力本身"
- 应归谁：直接开发 / 对应业务技能
- 判失败的信号：把"写功能"包装成"灰度"

### N02
- Prompt：`把配置里这个值改一下`
- 为什么不该触发：一次性改动，无可回退需求
- 应归谁：直接改配置
- 判失败的信号：为一个参数上开关框架

### N03
- Prompt：`用 hook 判断走新路还是老路`
- 为什么不该触发：负边界明写"不用钩子做判定"（判定落配置：进 git、跨端一致、可秒级回滚）
- 应归谁：配置开关
- 判失败的信号：把判定写进 hook

### N04
- Prompt：`把这次经验固化成技能`
- 为什么不该触发：归 `skill-evolution`
- 应归谁：skill-evolution

### N05
- Prompt：`资料库整理一下`
- 为什么不该触发：归 `space-hub`
- 应归谁：space-hub

### N06
- Prompt：`520 体检`
- 为什么不该触发：归 `inspect-hub`
- 应归谁：inspect-hub

## B 组 · 边界（B≥3）

### B01
- Prompt：`数据库表结构变更也灰度一下吧`
- 边界在哪：破坏性/不可回退变更**不属灰度**（负边界明写）
- 正确处置：走变更审批 + 备份 + 双写/迁移脚本预案；明说"这不是灰度能解决的"
- 判失败的信号：给 schema 变更套个开关就当安全了

### B02
- Prompt：`开关状态放数据库里方便动态改`
- 边界在哪：状态必须进 git（可审计、可回滚、换机不丢）
- 正确处置：状态放配置文件/常量并提交；需要"动态"时说明代价
- 判失败的信号：开关只在数据库/内存里

### B03
- Prompt：`这功能没法回退，但我想灰度`
- 边界在哪：不可回退 + 灰度 = 自相矛盾
- 正确处置：先把"不可回退"改成"可回退"（加开关/加兼容层），做不到就直说不适合灰度
- 判失败的信号：假装灰度实则全量

### B04
- Prompt：`全量上线吧，出问题再说`
- 边界在哪：用户有权决定，但必须知情
- 正确处置：明确列出"没有开关意味着出问题只能回滚代码/停机"，让用户在有信息的前提下决定
- 判失败的信号：不提示风险直接执行
